# MobileShowcase — спільний вхід телефона + смуги, гармонізована палітра

Друга ітерація по `components/sections/MobileShowcase.tsx`. Обидві зміни стосуються **лише
десктопа** (>1024px, sticky-пін) — мобільна версія лишилась як була.

---

## Задача 1 — телефон і смуга виїжджають як одна сцена

Раніше телефон крутився rotateY «на місці», а смуга взагалі не мала вхідної анімації —
просто висіла на своєму місці й паралаксила. Тепер обидва входять **з лівого нижнього кута**
в одному вікні скролу.

### Траєкторії

| | старт (progress 0) | фініш |
|---|---|---|
| смуга | `x −680px`, `y +190px`, `opacity 0` | `0, 0, 1` на **0.28** |
| телефон | `x −240px`, `y +140px`, `scale 0.9`, `rotateY −24°`, `rotateX 13°`, `opacity 0` | `0` на **0.34** |

Обидва рухаються приблизно вздовж діагоналі самої смуги, тому читаються як один рух, а не як
два незалежні елементи.

**Про stagger.** Спробував обидва варіанти, як ви й просили:

- *Синхронно* (однакова точка фінішу 0.34) — виглядає пласко: телефон і смуга рухаються як
  один жорсткий блок, немає відчуття причини й наслідку.
- *Смуга трохи попереду* (0.28 проти 0.34) — **залишив цей.** Смуга приходить першою й
  «підхоплює» телефон, який доїжджає на ній. Саме та метафора, яку ви описали.

`rotateY` на вході тепер **від'ємний** (−24° замість +24°): телефон нахилений у той бік, куди
летить, — провідна грань до глядача. З попереднім знаком він виглядав так, ніби їде спиною
вперед.

### Що збережено без змін

- Подальший дрейф телефону 0.34 → 1 (`rotateY 0 → −7°`, `rotateX 0 → 2°`).
- «Удари» смуги при зміні активного пункту (`x/rotate/scaleY` keyframes) + пружинне
  під'їжджання до активного рядка.
- Повільний паралакс смуги від скролу **всієї** сторінки.
- Перефарбування під активний пункт.

### Як це влаштовано

Смуга тепер має **три вкладені шари, по одному драйверу на кожен** — інакше вони переписують
один одному `transform`:

```
.ms-band-enter   → вхідний x/y/opacity  (progress секції)
.ms-band-outer   → паралакс x + rotate  (progress сторінки)
.ms-band         → y за активним рядком + «удар»  (imperative controls)
   └ .ms-band-fill / .ms-band-core  → колір активного пункту
```

Усі вхідні motion values беруться від `eased` (пружини), а не напряму зі `scrollYProgress` —
з тієї ж причини, що й у минулій ітерації: «чистий» ланцюжок scroll → властивість Motion
віддає нативній ScrollTimeline, чий діапазон не збігається з піном.

### Розмір смуги

Під макет: замість скромної смужки за списком — прямокутник на всю сцену.

| | було | стало (десктоп) |
|---|---|---|
| товщина | 88px | `30vh` (~третина висоти пін-сцени) |
| ширина | 116% колонки тексту | `200vw` |
| охоплення | тільки права колонка | далеко за телефон зліва й за екран справа |

Розміри у `vw/vh`, тому пропорції тримаються на будь-якому вьюпорті; обрізає `overflow: hidden`
на `.ms-pin`. Зсув `-46%` тягне яскраву середину градієнта з колонки тексту в бік телефона —
щоб смуга читалась як така, що **проходить під ним**, а не починається від нього.

## Задача 2 — гармонічніша палітра

Зробив **обидва** підходи, які ви пропонували, разом — окремо жоден не давав потрібного.

**(а) Градієнт, що перетікає у фон.** Кожен акцент тепер має дві версії: ядро (підмішано 20%
фонового тону) і краї (68%). Смуга йде `прозоро → край → ядро → край → прозоро`, тобто
насиченість падає до країв і стрічка розчиняється у сцені, а не впирається в межу.

**(б) Присаджена насиченість + blend.** Базовий тон `BAND_BASE = rgb(30, 29, 56)` —
десатурований індиго між `--bg` і `--bg-2`. Підмішування до нього одночасно знижує і
saturation, і lightness.

**Blend-mode: перевірив обидва, лишив `screen`.** На канві `#05060C` `soft-light` затемнює
значно сильніше, ніж підсвічує, — смуга практично зникає. `screen` із затемненими
(гармонізованими) тонами *додає* світло до фону замість того, щоб його перекривати — саме це
й прибирає ефект «чужорідного прямокутника». Перевірив інструментально: та сама точка дає
`rgb(97, 91, 78)` зі `screen` проти `rgb(10, 16, 14)` без нього, тобто блендинг реально
дістає до фону сторінки (вкладені `transform`/`opacity` могли б його ізолювати — не
ізолювали).

Уся логіка — три чисті функції: `harmonize()`, `bandFill()`, `bandCore()`. Додати новий пункт
можна, просто дописавши колір у `PILLARS` — гармонізація застосується сама.

### Дві правки, які знадобились по ходу

- **Смуга стала майже невидимою** після першого проходу гармонізації (`opacity 0.62`,
  сильно затемнені кольори), а тонка core-лінія перетворилась на випадкову подряпину через
  весь текст. Перебалансував: підняв присутність заливки, а core-лінію притишив до 0.16 і
  звузив до центральних 32% ширини.
- **Смуга ≠ перефарбовувалась.** У вашому ТЗ сказано «перефарбування смуги під колір
  активного пункту … лишити як є» — але фактично в минулій ітерації смуга мала **статичний**
  градієнт, під активний пункт перефарбовувались лише німб, риска й номер. Зробив так, як ви
  описали: смуга тепер теж бере колір активного пункту (гармонізований), плавний
  кросфейд 0.8s.

### Кольори активного пункту

Послідовність фіолетовий → індиго → синій → ціан лишилась. Самі акценти (номер, риска,
`text-shadow`, німб телефона) — **без змін**, поster-яскраві. Гармонізація застосована лише
там, де вона потрібна, — до смуги, бо вона велика.

## Мобільна версія — без змін

Тут я зробив свідому правку **проти** першої реалізації: нову геометрію смуги (200vw × 30vh)
я спершу поклав у базові стилі, і вона поїхала й на мобілку. Виправив — велика смуга тепер
живе **тільки** всередині `@media (min-width: 1024px)`, а базові стилі лишають мобільну
смужку такою, як була (116% × 88px), зі своїм балансом `opacity/blur`. Вхідних анімацій на
мобілці нема взагалі: `linked = false` → `style` не застосовується.

**Один виняток, який варто підтвердити.** Гармонізацію кольорів я застосував **скрізь**,
включно з мобілкою, хоча формально ви обмежили обидві задачі десктопом. Причина: колір
задається з JS одним `bandFill(accent)`, і тримати дві різні палітри для однієї смуги — це
радше баг, ніж фіча. Якщо хочете на мобілці стару «плакатну» палітру — скажіть, розділю.

## Перевірка

`npm run build` — успішно. Далі `npm run start` (продакшн-збірка) + headless Chrome у трьох
режимах.

| Перевірка | desktop | mobile | reduced-motion |
|---|---|---|---|
| Console errors / warnings / hydration | **порожньо** | **порожньо** | **порожньо** |
| Пін | `sticky` | `static` | `static` |
| Горизонтальне переповнення | 0px | 0px | 0px |
| Активний пункт по відрізках | `1/0.36/0.36/0.36` → `0.36/1/0.36/0.36` → `…/1` | усі 1.00 | усі 1.00 |
| Смуга виходить за екран (вьюпорт 1440) | `−844 … 1961` | `−29 … 375` (як була) | `−819 … 2061` |

Вхідна анімація по кадрах (вьюпорт 1440×900):

| progress | смуга | телефон |
|---|---|---|
| 0% | `translateX(−680) translateY(190)`, opacity 0 | `translateX(−240) translateY(140) scale(0.9) rotateY(−24°)`, opacity 0 |
| 15% | `translateX(−316) translateY(88)`, opacity 0.59 | `translateX(−134) translateY(78) scale(0.944) rotateY(−13.4°)`, opacity 1 |
| 34% | `none`, opacity 1 | `none` (залишкові <0.15px) |

Скріншоти: 3 кадри входу (0 / 15 / 34%), 2 фінальні стани з новою палітрою (пункт 02 —
індиго, пункт 04 — ціан, щоб було видно перефарбування) і мобільний екран для підтвердження,
що там нічого не змінилось — надіслані окремо.

## Що можна докрутити

- Смугу легко зробити помітнішою/тихішою одним числом — `.ms-band-fill { opacity }`
  (зараз 0.62 на десктопі, 0.9 на мобілці).
- Ступінь гармонізації — константи `BAND_MIX_CORE` (0.2) і `BAND_MIX_EDGE` (0.68): більше
  значення = ближче до фону, менше = ближче до чистого акценту.
- Довжину «випередження» смуги — `ENTER_BAND` (0.28) проти `ENTER_PHONE` (0.34).
