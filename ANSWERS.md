# Інтро-анімація логотипу — звіт про виконання

## Що зроблено

Реалізовано 4-фазну сплеш-анімацію логотипу, яка показується один раз за сесію браузера перед основним контентом сайту.

### Файли

| Файл | Що змінено |
|---|---|
| `components/site/IntroAnimation.tsx` | **Новий** клієнтський компонент — вся логіка анімації (замінив `components/site/IntroSplash.tsx`, який видалено) |
| `app/globals.css` | Додано стилі `.kd-intro-*` + keyframes `kd-caret-blink` для курсора; правило `html.intro-seen .kd-intro-overlay{display:none}` |
| `app/layout.tsx` | Імпорт `IntroAnimation` замість `IntroSplash`; блокуючий inline-скрипт у `<head>` оновлено під `sessionStorage`/`intro-shown` + перевірку `prefers-reduced-motion` |

Логотип узято з наявного файлу `app/logo/logo(1).svg` (нових файлів не створювалось) — імпортується як статичний asset (`import logoSrc from "@/app/logo/logo(1).svg"`), стандартний механізм Next.js для локальних зображень.

## Як це працює

**Таймлайн (реальний час):**

| Час | Що відбувається |
|---|---|
| 0–600мс | Лого з'являється по центру: opacity 0→1, scale 0.9→1 (у збільшеному стані ~150px), easing `cubic-bezier(0.16,1,0.3,1)` |
| 600–900мс | Пауза ~300мс — лого просто тримається на екрані |
| 900–1450мс | Лого одночасно зменшується до ~52px і "їде" ліворуч у складі групи; easing `cubic-bezier(0.65,0,0.35,1)` |
| 900–~1390мс | (паралельно) Текст "Kindratyak.dev" друкується по символу, ~35мс/символ, з блимаючим курсором |
| ~1790–2190мс | Весь інтро-блок (фон + лого + текст) плавно зникає (fade-out 400мс), відкриваючи сайт |

**Центрування групи "лого+текст" без ручної математики позицій:** контейнер — звичайний `display:flex; justify-content:center` навколо лого й тексту. Коли текст друкується (росте symbol за symbol), flexbox сам перераховує центр рядка на кожному кадрі — лого природно "зсувається" ліворуч від центру екрана рівно настільки, наскільки зростає текст поруч. Це саме той ефект "лого+текст як єдиний центрований лейбл", який вимагався, без обчислення пікселів вручну.

**Без layout shift:** зміна розміру лого (150px → 52px) реалізована виключно через CSS `transform: scale()` на елементі з фіксованим `width/height` — ширина/висота самого блоку ніколи не змінюються напряму, тільки трансформ.

**Курсор:** тонка вертикальна риска (`.kd-intro-caret`), блимає (`step`-анімація) лише поки йде друк (`data-blink="true"`), миттєво зникає (opacity: 0, без анімації) одразу по завершенню друку останнього символу.

## Технічні вимоги — як виконано

- **Framer Motion**: бібліотека вже була в `package.json` (`framer-motion ^12.38.0`) — використано `motion.div`/`motion.img` для fade/scale-переходів; фази тексту/друку — на `useState` + `setTimeout`/`setInterval`.
- **Один раз за сесію**: `sessionStorage.getItem('intro-shown')`, прапорець виставляється по завершенню фази 4 (і одразу, якщо спрацював `prefers-reduced-motion`). Через `sessionStorage` (не `localStorage`) інтро повториться в новій вкладці/сесії, як і вимагалось у ТЗ.
- **Anti-flash**: як і в попередній реалізації сайту, перед гідратацією виконується блокуючий inline-скрипт у `<head>` (`app/layout.tsx`), який ставить клас `intro-seen` на `<html>`, якщо прапорець вже є або увімкнено reduced-motion — CSS ховає оверлей ще до першого малювання, жодного "миготіння" анімації на повторних заходах.
- **`prefers-reduced-motion: reduce`**: перевіряється і в блокуючому скрипті (SSR-flash guard), і в самому компоненті — якщо увімкнено, інтро взагалі не рендериться, сайт показується миттєво.
- **`position: fixed; inset: 0`**, z-index (10000) вище решти контенту; `pointer-events: none` виставляється, щойно стартує fade-out (фаза 4), щоб клік по сайту під низом не блокувався зайвий час.
- **Скрол заблокований** на час інтро: `document.body.style.overflow = "hidden"`, знімається одразу по завершенню (і в cleanup-функції `useEffect`).
- **Адаптивність**: медіа-запит `@media (max-width: 640px)` зменшує базовий розмір лого (52px → 44px) і шрифт тексту (28px → 21px) та відстань між ними — фінальний "лейбл" не виходить за краї на мобільних.
- **Фон інтро**: суцільний `#0A0A2E`, без градієнтів, як і вказано в ТЗ.
- **Шрифт напису**: `var(--font-body)` (той самий Inter, що й на сайті), `font-weight: 500`, білий/near-white (`#F8F9FF`), `letter-spacing: 0.01em`.

## Як перевірити / повторити анімацію

Прапорець `sessionStorage` тримається, поки не закрити вкладку. Щоб примусово побачити інтро ще раз (наприклад, для дизайн-рев'ю), додайте до URL `?intro=1` — це працює незалежно від того, чи вже стоїть прапорець і чи увімкнено reduced-motion.

## Update: виправлення 3 багів

### Баг 1 — оверлей не розтягнутий на всю висоту на мобільному

**Факт-чек причини:** в коді `.kd-intro-overlay` ніде не використовувався `100vh` — оверлей мав лише `position: fixed; inset: 0`, без явного `height`. Тобто буквальна причина, названа в задачі ("використання 100vh"), у коді була відсутня. Але сам симптом (fixed-оверлей не гарантовано покриває видиму область, поки мобільний браузер анімує адресний рядок) — реальна, добре задокументована проблема саме для `position: fixed` з `inset:0`/без явного `height`, тому фікс застосовано превентивно:

```css
.kd-intro-overlay {
  position: fixed;
  inset: 0;
  width: 100%;
  height: 100vh;      /* фолбек для браузерів без dvh */
  height: 100dvh;      /* динамічна висота viewport — враховує адресний рядок */
  min-height: 100dvh;
  ...
}
```

Також перевірено (не потребувало змін):
- `position: fixed; inset: 0` дійсно стоїть на самому оверлеї (`app/layout.tsx`: `<IntroAnimation />` — перший дочірній елемент `<body>`, нічого не обгортає).
- Між `<body>` і `.kd-intro-overlay` немає жодного предка з `transform`/`filter`/`will-change: transform` — перевірено grep'ом по `app/layout.tsx` і структурі дерева, конфліктів немає.

**Перевірено:** `CSS.supports('height','100dvh')` → `true`; обчислена `getComputedStyle(overlay).height` точно дорівнює `window.innerHeight` (861px = 861px) у тестовому вікні. **Не вдалося перевірити:** справжню поведінку адресного рядка iOS Safari — `resize_window` у цьому remote-Chrome середовищі не змінює реальний розмір OS-вікна (перевірено двічі, viewport лишався 1920×861 незалежно від запитаних 390×700/390×844), а десктопний Chrome не має мобільного toolbar, тому `vh`/`dvh` в ньому завжди ідентичні. Рекомендація: фінальну перевірку зробити на реальному iOS-пристрої або через Chrome DevTools device toolbar (де dvh симулюється коректно).

### Баг 2 — анімація недостатньо плавна

- **Тільки transform/opacity:** перевірено всі `animate`-пропси Framer Motion (`opacity`, `scale`) — жодних `width`/`top`/`left`/`font-size`. Знайдено один реальний відхил від правила: `.kd-intro-group[data-active="true"] { gap: 14px }` з `transition: gap 0.3s` — `gap` є layout-властивістю (викликає reflow), тож приберано разом з даним фіксом: тепер `gap: 14px` — константа від самого початку (без transition), а сам текстовий `<span>` монтується/розмонтовується через React (`TypewriterText` повертає `null`, поки друк не почався), тож "стрибка" gap не видно — текст просто з'являється з уже готовим відступом.
- **will-change:** додано `will-change: opacity` на `.kd-intro-overlay`, `will-change: opacity, transform` на `.kd-intro-glow` і `will-change: opacity` на `.kd-intro-text` (у `.kd-intro-logo` вже було). Прибирання через `useEffect`-cleanup свідомо не робили: весь оверлей (разом з усіма цими елементами) **повністю розмонтовується** через React (`if (gone) return null`) одразу по завершенню фази 4 — DOM-вузли, а з ними і будь-які GPU-шари від `will-change`, знищуються остаточно. Це надійніший спосіб звільнити шар, ніж вручну перемикати inline-стиль (менше шансів залишити "протухлий" `will-change`, якщо cleanup-логіка десь дасть збій).
- **Конфлікт Framer Motion + CSS-transition на одному елементі:** перевірено — на жодному `motion.*`-елементі не висить паралельний CSS `transition`. Єдиний випадок, коли CSS-transition (`gap`) співіснував у часі з `motion`-анімацією на **сусідньому** (не тому самому) елементі — усунено видаленням transition на `gap` (див. вище).
- **React.memo для друкарської машинки:** `setInterval` кожні 35мс раніше оновлював `typedCount`/`typing` у самому `IntroAnimation`, тобто кожен тік передруковував увесь компонент — включно з `motion.img` лого й `motion.div` світінням, яким на кожному рендері діставався **новий об'єкт** `transition={...}` (створюваний інлайн), що зайве навантажувало Framer Motion під час паралельної transform-анімації. Винесено у новий `TypewriterText = memo(...)` — окремий компонент зі своїм `useState`/`setInterval`; `IntroAnimation` передає йому лише стабільний `boolean` (`start={shrink}`), тому батьківський компонент більше не ре-рендериться на кожен символ.

  **Перевірено емпірично** (тимчасове `console.log` на рендерах обох компонентів, прибрано після перевірки): в одній і тій самій ділянці логу `TypewriterText` рендерився кілька разів поспіль (символ за символом) **без жодного відповідного рендеру `IntroAnimation` між ними** — пряме підтвердження, що батьківський компонент (і, відповідно, лого/оверлей/світіння) більше не тригериться тіками друкарської машинки.

- **FPS / Chrome DevTools Performance:** тут довелось зіткнутись з обмеженням тестового середовища. Спроба виміряти реальний FPS через `requestAnimationFrame`-семпли (аналог того, що показав би Performance-запис) підвисла на 45с — з'ясувалось, що автоматизована вкладка Chrome у цьому оточенні має `document.visibilityState === "hidden"` / `hasFocus() === false` (вона не є активним "видимим" вікном на рівні ОС), а браузери **повністю призупиняють** `requestAnimationFrame` для прихованих вкладок (це стандартна поведінка Chrome, не баг сайту). Через це неможливо було зняти справжній Performance-трейс чи `rAF`-based FPS у цій сесії — рекомендація: прогнати `Performance recording` вручну в звичайному (видимому) вікні Chrome, чи на реальному мобільному пристрої.

### Баг 3 — flash контенту на 30–50мс перед стартом анімації

Це був **реальний і підтверджений** баг. Причина: компонент повертав `null`, поки `useEffect` не встигав виставити `shouldRender=true` — а `useEffect` виконується вже **після** першого комміту/пейнта (це асинхронний post-paint хук), тобто між першим пейнтом сторінки (де оверлея ще нема в DOM) і моментом, коли React домонтовував оверлей, дійсно існувало вікно, де під низом міг промайнути контент сайту.

**Фікс:** оверлей тепер рендериться **безумовно** за замовчуванням (єдиний гейт — `gone`, який стартує `false`), тобто він частина самого server-rendered HTML і найпершого пейнта — без очікування на клієнтський ефект. `useEffect` тепер відповідає лише за (а) рішення "показувати чи скіпнути" (already-seen/reduced-motion) і (б) запуск таймерів фаз.

Це навмисно **інша реалізація**, ніж запропонований у задачі варіант (окремий inline `<style>` у `<head>`, що форсить `.kd-intro-overlay{opacity:1!important;display:flex!important}`) — такий `<style>`-хак виявився зайвим, тому що тепер оверлей і без нього гарантовано присутній у сирому HTML. Два незалежні джерела правди для однієї й тієї ж видимості (React-рендер + окремий forced-CSS override) — це складніше підтримувати й легше неявно розсинхронізувати; наявний механізм (блокуючий `<script>` в `<head>` + клас `intro-seen` в CSS) вже коректно обробляє **протилежний** випадок (коли треба сховати оверлей на повторному заході) тим самим прийомом, тож логіка лишається симетричною й з одним джерелом правди.

**Перевірено:**
- `curl` сирого SSR HTML (`npm run start`, продакшн-білд) → `.kd-intro-overlay` присутній у розмітці, і лого вже має інлайновий стиль `opacity:0;transform:scale(2.565)` — тобто "заморожений" перший кадр анімації запечений просто в HTML, до будь-якого JS.
- `IntroAnimation` — перший дочірній елемент `<body>` в `app/layout.tsx` (уже так було, змін не знадобилось); жодного `<Suspense>`, що міг би затримати його рендер, у дереві немає (перевірено grep'ом — `Suspense` в проєкті взагалі не використовується; `next/dynamic({ssr:false})` є лише в `GlobalParticles`/`Hero`-піддереві, які є сусідами оверлея, а не його предками, тож на нього не впливають).
- Throttled-network перевірку (Slow 4G у DevTools) окремо не проганяли — але оскільки фікс робить видимість оверлея структурною властивістю самого HTML/CSS (а не результатом виконання JS до певного дедлайну), відсутність flash тепер **не залежить від швидкості мережі чи завантаження JS** в принципі — це сильніша гарантія, ніж "перевірено й встигає на Slow 4G".

### Підсумок перевірки

- `npx tsc --noEmit` — без помилок.
- `npm run build` — production build проходить успішно.
- Повний прогін через `npm run start` (продакшн-режим, не dev) — послідовність фаз 1–4 відтворюється коректно, повторний захід без `?intro=1` пропускає інтро миттєво, без миготіння.
- Обмеження тестового середовища (чесно, щоб не видавати непідтверджене за перевірене): справжній мобільний viewport (адресний рядок Safari) і DevTools Performance/`rAF`-FPS трейс **не вдалося** відтворити в цій remote-Chrome сесії (вкладка automation — прихована/невидима вкладка на рівні ОС, що блокує `requestAnimationFrame`, а `resize_window` не змінює реальний розмір вікна). Рекомендовано дозняти обидва пункти на реальному пристрої/у звичайному вікні Chrome перед фінальним sign-off.
